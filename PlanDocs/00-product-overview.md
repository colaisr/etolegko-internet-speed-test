# Общее описание продукта: Legko (обёртка Keitaro)

> **Статус:** актуален (2026-11-19, фаза A–B закрыты). **Главная ценность:** симулятор сплита — байер собирает микс и веса **до** применения в Keitaro, смотрит diff и только потом Push. Источники: [Notion ТЗ](../PlanDocs/interview/sources/2026-11-19-adrobot-tz-notion.md), [видео-логика](../PlanDocs/interview/sources/2026-11-19-keitaro-wrapper-video-notes.md).

## 1. Краткая суть

**Legko** — рабочее место **медиабайера** для типовых кампаний в Keitaro: быстро завести кампанию по шаблону компании и **безопасно** крутить состав и доли офферов в потоке ротации, не лазая в полную админку трекера.

**Не цель:** заменить Keitaro или продублировать все его экраны.

**Цель:** снять с человека риск и рутину в двух частых операциях — «завести кампанию как у нас принято» и «поменять микс офферов и веса, не уронив трафик».

**Ценность одной метафорой:** для ротации офферов Legko — **симулятор сплита** (песочница конфигурации). Байер «играет» составом и процентами в обёртке; Keitaro получает изменения только после **осознанного Push**. Это не прогноз кликов/статистики — это предпросмотр **того, что уйдёт в трекер**.

## 2. Зачем обёртка, если есть Keitaro

Keitaro — сильный трекер, но для ежедневной работы байера это **тяжёлый универсальный инструмент**: много сущностей, потоков, фильтров; сохранение в админке по сути сразу меняет боевую конфигурацию; веса и ротация офферов требуют внимания к «цифрам на 100%».

По видео заказчика видно **осознанную модель продукта**, а не «ещё один UI»:

| Идея | Ценность для пользователя |
| --- | --- |
| **Черновик → Push** | Можно набрать офферы, пересчитать веса, откатить (Cancel), и только потом вывести в Keitaro. Меньше «случайно сохранил и поломал сплит». |
| **Жёлтый / белый поток** | Понятно, где локальные изменения и где Keitaro ещё старый — не нужно помнить «я уже пушил или нет». |
| **Remove + архив + Bring back** | Удаление не стирает историю в обёртке; можно вернуть оффер в микс без поиска в Keitaro. |
| **Fetch и статус removed** | Если коллега правил кампанию в Keitaro, повторный Fetch не врёт «всё ок» — расхождение видно как removed. |
| **Pin веса** | Закрепить долю сильного оффера; остальное пересчитывается — рутинная математика, которую легко ошибить руками. |
| **Потоки без офферов «в тени»** | Geo → Google и прочие служебные потоки не отвлекают; байер видит то, чем реально управляет — **ротацию офферов**. |

**Создаватор** добавляет ценность **шаблона**: один ввод (имя, geo, offer) → в Keitaro сразу правильная **двухпоточная** схема (geo на Google, остальное на оффер) плюс домен / группа / источник. Без прохождения десятка экранов и без типовой ошибки «забыл фильтр по стране».

## 3. Пользователь

**Основной:** медиабайер / трафик-менеджер, который:

- запускает и крутит связки под арбитраж;
- знает ID офферов и geo, но **не хочет** быть админом Keitaro;
- отвечает за то, чтобы сплит офферов был корректным и изменения не улетали в прод случайно.

**Вторичный (позже):** тимлид, который проверяет «есть черновики / расхождение с Keitaro» — в MVP не обязателен.

## 4. Главные «работы» (jobs to be done)

1. **Завести кампанию по стандарту компании** за минуты, а не собирать потоки руками в Keitaro.
2. **Спланировать новый микс офферов** (добавить, убрать, закрепить вес), убедиться что **проценты сходятся**, затем **одним действием** отдать в Keitaro.
3. **Понять рассинхрон** с Keitaro после чужих правок и привести картину к правде через Fetch, не теряя контекст в обёртке.

## 5. Что значит «лучше, чем на видео» (направление для MVP+)

Тестовое можно сдать «как на видео», но продуктовая ценность усиливается, если:

| Улучшение | Зачем |
| --- | --- |
| **Проверка перед Push** | Сумма весов = 100%, есть хотя бы один активный оффер; явные ошибки до вызова API. |
| **Краткий «что изменится»** перед Push | Список: добавить / убрать / сменить вес — байер подписывается осознанно. |
| **Статус кампании** | «Синхронно» / «Есть черновик» / «Keitaro изменился — нужен Fetch» — без жонглирования цветами в голове. |
| **Создаватор: результат** | После создания — ссылка кампании, что выбрано для домена/группы/источника (прозрачность, не чёрный ящик). |
| **Поиск оффера по имени** | Не только голый ID — меньше ошибок и переключений в Keitaro. |
| **Понятные пустые состояния** | Первый Fetch, нет офферов, всё removed — что делать дальше. |

В MVP входят **логика видео** и **обязательные гейдрейлы**: проверка весов перед Push, diff, статусы синхронизации, прозрачный создаватель, поиск оффера. Без них продукт не имеет смысла (см. [`25-mvp-plan.md`](25-mvp-plan.md)). Локальное состояние — **SQLite** ([`15-architecture.md`](15-architecture.md)).

## 6. Scope тестового задания (внешнее ТЗ)

Две обязательные части от заказчика:

1. **Создаватор кампаний** — имя, geo, offer ID → кампания с 2 потоками и настройками домена/группы/источника.
2. **Редактор кампании** — add/remove офферов в духе видео; UI на наш вкус; **кнопки и цифры верные**.

Детали по фичам: [`01-campaign-creator.md`](01-campaign-creator.md), [`02-stream-offer-editor.md`](02-stream-offer-editor.md).

## 7. Термины

| Термин | Значение |
| --- | --- |
| **Keitaro** | Внешний трекер; источник правды **после Push**. |
| **Обёртка / Legko** | Наш сервис + локальное состояние черновиков. |
| **Поток (stream)** | Ветка маршрутизации в кампании Keitaro. |
| **Оффер-поток** | Поток с ротацией офферов; то, что редактируем в UI. |
| **Служебный поток** | Например geo → Google; в UI только факт существования. |
| **Push** | Применить черновик к Keitaro. |
| **Fetch** | Подтянуть потоки из Keitaro и согласовать с локальной моделью. |

## 8. Вне MVP (на потом)

- Мультипользователь, роли, audit log «кто пушил».
- Список всех кампаний, аналитика Keitaro внутри обёртки.
- Редактирование служебных потоков и фильтров в UI.
- Полная замена админки Keitaro.

# Редактор офферов (симулятор сплита)

> **Статус:** актуален (2026-11-19, фаза B закрыта). **Для MVP:** обязательно. Сводка: [`29-mvp-functional-description.md`](29-mvp-functional-description.md) §4–5. Эталон: [видео](../PlanDocs/interview/sources/2026-11-19-keitaro-wrapper-video-notes.md).

## 1. Зачем пользователю

**Симулятор:** весь микс офферов и **%** живут в обёртке до **Push**. Байер может:

- добавить/убрать/вернуть офферы;
- закрепить вес;
- **отменить** эксперимент (**Cancel**);
- **увидеть diff** и только потом включить конфиг в Keitaro.

Keitaro **не меняется**, пока байер не подтвердил Push.

## 2. Вход на экран

- Из создавателя после Create.
- По **ID кампании в Keitaro** (поле на старте).
- Из списка **«Недавние»** (кампании, созданные/открытые в этой установке Legko).
- Сразу после Create — **автопереход** без повторного ввода id.

**Fetch:** после Create — **автоматически**; далее только кнопкой **Fetch Streams** (явное «сверить с Keitaro»).

## 3. Макет экрана (логика, не дизайн)

```
[ Шапка: имя | id | URL | статус бейдж ]
[ Fetch Streams ]
[ Служебный поток — не редактируется ]
[ Оффер-поток — белый/жёлтый ]
    Таблица: оффер | % | pin | статус | действия
    Add offer (поиск)
[ Cancel ] [ Push to Keitaro ]
```

## 4. Статусы

### Кампания (бейдж)

| Статус | Когда |
| --- | --- |
| **Синхронно** | Нет черновика в оффер-потоке; совпадает с последним Push |
| **Есть черновик** | Жёлтый поток или локальные изменения после последнего Push |
| **Проверьте Keitaro** | После Fetch с removed из-за drift (опционально: напоминание, если давно не Fetch) |

### Поток офферов

| Визуал | Смысл |
| --- | --- |
| Белый | Keitaro = последний Push |
| Жёлтый | Есть что пушить или отменить |

### Оффер

| Статус | % | Действия |
| --- | --- | --- |
| active | >0 | Remove, Pin |
| removed | 0, серый | Bring back |

## 5. Операции (детально)

### Fetch Streams

- Тянет потоки из Keitaro.
- **Оффер-поток:** список офферов и веса согласуются с Keitaro; локальные черновики **не затираются без правила** — при первом Fetch после create: залить из Keitaro; при Fetch с drift: пропавшие → removed.
- **Служебный поток:** только «существует», без URL/фильтров.

### Add offer

- Поиск по имени/id через API.
- Добавляет строку, **пересчитывает** веса активных (pin не трогает).
- Поток **жёлтый**. Keitaro **без изменений**.

### Remove

- Soft-delete: 0%, серый, в архиве локально.
- Пересчёт остальных. Жёлтый.

### Bring back

- Возврат в active, пересчёт. Жёлтый.

### Pin weight

- Фиксирует %; дальнейший add/remove пересчитывает **только незапиненные**; сумма **100%**.

### Cancel

- Откат к состоянию **после последнего успешного Push** (локально).
- Keitaro не трогается. Белый.

### Push to Keitaro

1. Валидация: ≥1 active, сумма % = 100.
2. **Diff:** добавления, удаления, изменения весов в Keitaro.
3. Подтверждение → API → при успехе: белый, обновить слепок, бейдж «Синхронно».
4. При ошибке: жёлтый остаётся, сообщение, можно повторить.

## 6. Правила пересчёта весов

- База: **равномерное** распределение 100% между **active** с pin.
- **Округление:** **largest remainder** — целые проценты, сумма **ровно 100%** ([`29` §10](29-mvp-functional-description.md)).
- Remove не участвует в делении до bring back.

## 7. Сценарии + ценность

| # | Сценарий | Ценность |
| --- | --- | --- |
| 1 | Add несколько → смотрю % → diff → Push | Видел будущий сплит до боя |
| 2 | Remove слабого → Push | Убрал из Keitaro через песочницу |
| 3 | Несколько Add → Cancel | Игра без последствий |
| 4 | Fetch после правок в Keitaro | Правда о расхождении |
| 5 | Pin лидера → Add ещё | Контроль доли без Excel |

## 8. Ошибки и пустые состояния

| Состояние | UI |
| --- | --- |
| Не было Fetch | CTA Fetch |
| Push disabled | Причина: «≠100%» / «нет активных» |
| API error on Push | Черновик сохранён |
| Поиск оффера — ничего | Подсказка |

## 9. Вне MVP

Редакт geo→Google, несколько оффер-потоков, 2 пользователя, статистика.

## 10. Приёмка
